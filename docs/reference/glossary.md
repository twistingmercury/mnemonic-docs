# Glossary

> Back to [Project README](../../README.md)

Definitions of key terms used throughout the Mnemonic documentation. Terms are listed alphabetically.

---

**Agent**
A named entity in Mnemonic representing a Claude Code agent role (e.g., `go-engineer`, `devops-engineer`). Patterns are associated with agents via relevance scores (0.0--1.0) so that search results can be filtered by agent context. Agent definitions are managed externally in version-controlled repositories; Mnemonic stores only the name and a JSONB definition blob.
See also: [Pattern](#pattern), [Knowledge Graph](#knowledge-graph)

**Chunk**
A decorated section of a pattern file that is independently vectorized and indexed for semantic search. Chunks are created by splitting pattern content at H2/H3 headings marked with the `[//]: pattern` decorator. Each chunk gets its own embedding stored in the `pattern_chunks` database table.
See also: [Decorator](#decorator), [Embedding](#embedding), [Pattern File](#pattern-file)

**Cosine Similarity**
A measure of similarity between two vectors, calculated as the cosine of the angle between them. Values range from 0.0 (orthogonal/unrelated) to 1.0 (identical direction). Mnemonic uses PGVector's `<=>` operator to compute cosine similarity between chunk embeddings and query embeddings.
See also: [Embedding](#embedding), [PGVector](#pgvector)

**Decorator**
The exact string `[//]: pattern` placed on its own line immediately before an H2 or H3 heading in a pattern file. Decorators mark sections for chunking and vectorization. Sections without decorators are discarded during indexing. The `## Overview` section must not be decorated.
See also: [Chunk](#chunk), [Pattern File](#pattern-file)

**Embedding**
A numeric vector (array of 2000 floating-point numbers) that represents the semantic meaning of text. Generated by OpenAI's `text-embedding-3-large` model with Matryoshka truncation to 2000 dimensions. Similar texts produce similar embeddings, enabling semantic search via cosine similarity.
See also: [Cosine Similarity](#cosine-similarity), [Enrichment](#enrichment), [PGVector](#pgvector)

**Enrichment**
The asynchronous pipeline that transforms a raw pattern into a searchable, interconnected knowledge entry. The pipeline has five steps: (1) validate and store metadata, (2) generate embeddings for each chunk via OpenAI, (3) extract concepts via OpenAI, (4) create Neo4j relationships, (5) update status. Enrichment status tracks as `pending`, `enriched`, or `failed`. Only enriched patterns appear in search results.
See also: [Chunk](#chunk), [Embedding](#embedding), [Knowledge Graph](#knowledge-graph)

**Frontmatter**
The YAML metadata block at the top of a pattern file, delimited by `---`. Contains required fields (`name`, `entity_type`, `language`, `domain`, `description`) and optional fields (`agents`, `tags`, `version`, `related_patterns`). See the [Pattern File Schema](pattern-schema.md) for the full specification.
See also: [Pattern File](#pattern-file)

**HNSW**
Hierarchical Navigable Small World. A vector index algorithm used by PGVector for approximate nearest-neighbor search on chunk embeddings. Chosen over IVFFlat for chunk-level search because it provides better recall without requiring periodic retraining.
See also: [IVFFlat](#ivfflat), [PGVector](#pgvector), [Chunk](#chunk)

**IVFFlat**
Inverted File with Flat compression. A vector index algorithm that partitions embeddings into clusters via k-means, then searches only the nearest clusters at query time. Previously used for pattern-level embeddings; now deprecated in favor of HNSW on chunks.
See also: [HNSW](#hnsw), [PGVector](#pgvector)

**Knowledge Graph**
The combination of Neo4j graph relationships and PostgreSQL vector data that represents the semantic structure of the pattern library. Nodes include `Pattern`, `Agent`, and `Concept`. Relationships include `RELEVANT_FOR` (Pattern to Agent), `RELATED_TO` (Pattern to Pattern), and `HAS_CONCEPT` (Pattern to Concept).
See also: [Agent](#agent), [Pattern](#pattern), [Enrichment](#enrichment)

**MCP (Model Context Protocol)**
The protocol Claude Code uses to communicate with external tool servers. Mnemonic exposes three read-only MCP tools (`search_patterns`, `find_related_patterns`, `get_pattern`) via Streamable HTTP on port 8081. Claude Code discovers and invokes these tools automatically during conversation.
See also: [Streamable HTTP](#streamable-http)

**Pattern**
A Markdown document with YAML frontmatter that captures a piece of team knowledge -- a coding convention, architectural decision, best practice, or design pattern. Patterns are the core unit of knowledge in Mnemonic. They are stored in PostgreSQL, chunked and vectorized for semantic search, and projected into Neo4j for graph traversal.
See also: [Pattern File](#pattern-file), [Chunk](#chunk), [Enrichment](#enrichment)

**Pattern File**
The on-disk Markdown format for patterns. Consists of YAML frontmatter followed by an `## Overview` section (excluded from indexing) and one or more decorated sections (indexed as chunks). Validated by `install/validate.sh`. See the [Pattern File Schema](pattern-schema.md) for the full specification.
See also: [Frontmatter](#frontmatter), [Decorator](#decorator), [Chunk](#chunk)

**PGVector**
A PostgreSQL extension that adds vector data types and similarity search operators. Mnemonic uses PGVector to store embeddings as `vector(2000)` columns and to perform cosine similarity searches using the `<=>` operator with HNSW indexes.
See also: [Embedding](#embedding), [HNSW](#hnsw), [Cosine Similarity](#cosine-similarity)

**Streamable HTTP**
The MCP transport protocol used by Mnemonic. Claude Code connects to `http://localhost:8081/mcp` and sends JSON-RPC 2.0 messages. Mnemonic runs in stateless mode (no session persistence).
See also: [MCP (Model Context Protocol)](#mcp-model-context-protocol)
